# CrossApp

Наскрізний проєкт з практикуму крос-платформного програмування.

## Предметна область

- **Назва**: Склад
- **Сутності**: `Product` (товар), `StockBatch` (партія), `Warehouse` (склад), `Movement` (переміщення)
- **Призначення**: Облік залишків товарів за партіями та відстеження їх переміщення між складами.

## Структура solution

- `src/Core` — бібліотека класів (бізнес-логіка, доменні моделі, розбір даних, сховища, сервіси та аналітичні звіти)
  - `Core/Abstractions/` — інтерфейси та контракти взаємодії (`ICatalogStore`, `INotificationSink`)
  - `Core/Domain/` — сутності з поведінкою та захистом інваріантів (`Product`)
  - `Core/Dto/` — незмінні DTO-моделі для перенесення й зберігання даних (`ProductDto`, `ImportResult<T>`)
  - `Core/Events/` — аргументи подій зміни стану каталогу (`CatalogChangedEventArgs`, `CatalogChangeKind`)
  - `Core/Storage/` — реалізації сховищ даних (`InMemoryCatalogStore`, `FileCatalogStore`)
  - `Core/Services/` — сервісний шар бізнес-операцій (`CatalogService`)
  - `Core/Reports/` — сервіс аналітичних звітів на базі LINQ to Objects (`ReportService`) та незмінні DTO звітів (`StockLine`, `GroupSummary`)
  - `Core/Import/` — розбір файлів CSV/JSON за допомогою pattern matching (`ProductCsvImporter`)
- `src/Cli` — консольний інтерфейс користувача (Composition Root, точка входу, підкоманди звітів та демонстраційні сценарії)
- `data/` — тестові набори даних (`sample.csv`, `catalog.json`)

## Доменна модель та Сервісний шар

### Інваріанти сутності (`Product`)

1. **Обов'язковість рядкових полів** (`ArgumentException`): ідентифікатор `Id`, `Sku`, назва `Name` та одиниця виміру `Unit` не можуть бути `null`, порожніми або складатись лише з пробілів.
2. **Невід'ємний початковий залишок** (`ArgumentOutOfRangeException`): початкова кількість товару під час створення через фабрику `Create` не може бути меншою за 0.
3. **Коректність операцій приходу та видачі** (`ArgumentOutOfRangeException`): передана кількість товару для операцій `RegisterArrival` та `Issue` повинна бути строго більшою за нуль.
4. **Заборона перевитрати товару** (`InvalidOperationException`): операція `Issue` не дозволяє списати або видати товару більше, ніж є на поточному залишку (`amount <= _quantity`).

### Сервіси та Сховища (Lab 05–06)

- **Контракт сховища**: `ICatalogStore` ізолює доменну логіку та сервіси від конкретного способу збереження даних (`List`, `GetById`, `Add`, `Update`, `Remove`).
- **Реалізації сховища**:
  - `InMemoryCatalogStore` — збереження залишків у пам'яті (`Dictionary<string, Product>`), наповнюється тестовими даними з `SampleData` (17 записів у 4 одиницях виміру).
  - `FileCatalogStore` — файлове JSON-сховище (`data/catalog.json`) з кешуванням у пам'яті та автоматичним скиданням змін на диск (`Flush`).
- **Сервісний шар**: `CatalogService` реалізує прикладні сценарії (`Add`, `Receive`, `Issue`, `All`, `Find`, `Delete`), працює виключно через `ICatalogStore` та генерує подію `Changed` при зміні залишків.

### Аналітичні звіти та LINQ (Lab 07)

- **Ізоляція контрактів**: логіка побудови звітів винесена в `ReportService` (приймає `IEnumerable<Product>`) і повертає незмінні `record`-DTO (`StockLine`, `GroupSummary`) або іменований кортеж замість доменних сутностей.
- **Реалізовані запити**:
  - `TopByQuantity` — топ-$N$ товарів за найбільшим залишком із детермінованим порядком (`OrderByDescending` + `ThenBy` за `Sku`).
  - `LowStock` — фільтрація дефіцитних позицій (`Where` за порогом `< 10`) з проєкцією у `StockLine`.
  - `ByUnit` — групування товарів за одиницею виміру (`GroupBy` без урахування регістру) з підрахунком кількості позицій та сумарного залишку.
  - `Totals` — обчислення зведених агрегатів (кількість позицій, загальна сума, середній та максимальний залишок) з безпечною обробкою порожньої колекції без винятку `InvalidOperationException`.

#### Відкладене виконання (Deferred Execution)

Оператори `Where`, `Select`, `OrderBy` та `GroupBy` у LINQ to Objects не виконують обчислень у момент оголошення запиту — вони лише конструюють план його виконання. Фактична ітерація по джерелу починається під час виклику завершальних методів (`ToList()`, `Count()`, `Sum()`) або в циклі `foreach`. У демонстрації відкладеного виконання перший виклик `query.Count()` проходить початковий список `source` і повертає кількість дефіцитних позицій до змін (4), а після додавання нового товару через `source.Add(...)` другий виклик `query.Count()` повторно виконує запит над оновленою колекцією та повертає вже нове значення (5). Після виклику `.ToList()` результат матеріалізується в окремий список `snapshot`, тому подальше очищення `source.Clear()` більше не впливає на зафіксовані дані.

#### Порівняння синтаксису запитів (Query Syntax vs Method Syntax)

У методі `ByUnitQuerySyntax` групування реалізовано через декларативний синтаксис запитів (`from ... group ... into ... select`), який візуально нагадує SQL і робить структуру групування та обчислення проміжних змінних (`let`) прозорішою. Проте ланцюжок методів (`Method Syntax`) у `ByUnit` залишається зручнішим на практиці, оскільки дозволяє передавати `StringComparer.OrdinalIgnoreCase` напряму в `GroupBy` без зміни регістру ключів та легше комбінується з методами на кшталт `Take()` чи власним `TopBy()`
